# 並列実行（v0.1.14）

v0.1.14で追加した機能です。サーバーの更新後に利用できます。

## 実行・待機

- 同じモデルも異なるモデルも、要求ごとにワーカーを占有して処理します。重みの保存ファイルは共通ですが、推論プロセスとRAM/VRAMは要求数に応じて増えます。字幕、入出力ストリーム、取消は要求単位です。
- 既定は最大10件、リアルタイム予約2枠、GPU最大2件。リアルタイムを先に選び、同じ用途内はclientIdを交替して選びます。clientIdは認証・利用者識別ではありません。
- ファイル処理は最大8件かつ全体予算の80%まで。リアルタイム用に実行枠とメモリ予算を残します。ファイル要求が待機中はリアルタイムだけで全枠を占有しません。実行中の処理を中断する優先制御ではなく、即時開始や一定の応答時間を保証しません。
- モデル別に、前処理・話者分離・GPU失敗後のCPU再試行を含む保守的なRAM/VRAM見積りで開始を判断します。同じモデルの複数ロードも個別計上します。GPU容量未確認かつ上限未設定なら「自動」は実行前にCPUを選択します。明示GPU、未知のモデル、予算不足は理由付きで待機し、他の実行可能な要求を先に処理します。
- 手動常駐モデルも予算に含めます。file/realtimeの手動常駐は従来の2枠のまま、合致するモデル・処理方法・用途の要求が空いている常駐枠を再利用します。他の要求のために常駐モデルを無条件に破棄しません。
- 自動ロードは要求終了時に解放します。子プロセスを含む終了確認ができるまで予約を返さず、終了未確認なら枠と予算を隔離して再利用しません。手動常駐は成功後も維持します。
- リアルタイムの1要求30秒制限は従来どおりです。10件並列は10本の永続ストリーミング接続や10倍の速度を意味しません。

## 設定

管理画面の「設定・更新」→「並列処理」で設定します。変更は実行・待機・アップロード・モデル操作・更新がすべて終了してから行います。資源待ち解消のために設定を変更する場合は、先にクライアント側で待機要求を中止してください。

| JSON項目 | 既定 | 意味 |
|---|---:|---|
| `maxJobs` | 10 | 最大同時実行数（2〜10） |
| `realtimeReserved` | 2 | リアルタイム用予約（1〜maxJobs未満） |
| `maxGpuJobs` | 2 | GPUジョブ上限（1〜maxJobs） |
| `ramLimitMiB` | 0 | 0は物理RAMの75%。明示値も物理RAMを超えない |
| `vramLimitMiB` | 0 | 0は検出NVIDIA VRAMの80%。未検出時は自動ならCPUへ切替、明示GPUなら待機 |

保存場所は`settings.json`内の`execution`。UIはGB、API/保存はMiBです。複数GPUの容量は合算せず最小の検出容量を採用します。自動検出できないVulkan等は管理者がVRAM上限を設定します。検出容量がある場合、明示上限もその容量を超えません。GPUデバイス番号の分散割当は未対応です。

OSの空きRAMも開始時に確認します。未反映の同時ロード予約を含め保守的に判定するため、空きがあっても待機になる場合があります。VRAM予算は本サーバーの予約の合計で、別アプリのGPU使用量を常時監視・強制制限する機能ではありません。実使用量は精度形式や音声長などで変わり、見積りは実消費の保証値ではありません。

未指定の推論CPUスレッド数は論理コア数÷最大並列数（1〜4）。既存の明示`threads`は優先します。Whisper・speech.cppへ反映し、NeMo-Speech.cpp等の内部並列度はそのランタイムに依存します。

## API追加（protocolVersion=3維持）

- `GET /api/health`の`capabilities.concurrentInference`、`resourceBudgetScheduling`で検出します。
- `GET /api/scheduling`は設定、有効予算、予約使用量、常駐量、実行ワーカー、ジョブID別待機理由を返します。`memoryPolicy=estimated-admission`です。
- `GET /api/status`と`GET /api/management`の`scheduling`でも取得できます。従来の`workers`は互換用のfile/realtime分類。物理ワーカー数は`activeWorkers`を使います。`gpuPolicy=budgeted-parallel`です。
- `POST /api/management/scheduling`へ上表の設定オブジェクトを渡します。既存の操作トークン/Bearer認証、接続元・Origin制限を使用。処理中・常駐モデルが新予算を超える場合は409、不正値や必須設定欠落は400です。保存成功後に反映。設定JSONの未知項目を保持し、個別インスタンスも再起動後に読み込みます。
- `GET /api/models`と`/v1/models`の`x_meeting.modelInfo`に`execution: {running,file,realtime}`を追加。公開カタログにはジョブID・本文を含めません。
- 資源待ちは`status=queued, phase=waiting_resources`、理由は`metadata.waitingReason`。`workerIndex`と`memoryReservation`は割当後の診断値です。クライアントは未知のphaseでもstatusを使い待機表示してください。
- 時間は既存の`queueSeconds`・`resourceWaitSeconds`・`runSeconds`へ分離して保存。待機中の`startedAt`は未設定です。

## 検証範囲

合成HTTP試験は同一/異なるWhisperモデルの10件同時開始、11件目待機、リアルタイム優先、RAM/VRAM予算、個別中止と結果分離、設定保存/欠落拒否を確認します。実モデルはコピーしたWhisper Tinyと合成音声を使い、専用ポート・設定・DB・モデルキャッシュで検証します。

実GPUの同時推論、大型モデル5〜10件、異なるエンジンを混在させた実推論、長時間負荷の性能は未確認です。M4000や19GBモデルの取得・再試験は今回の検証に含めません。
