# 再起動後の再実行と完了待ち停止（v0.1.15）

v0.1.15で追加した機能です。利用アプリ側も結果世代の変更に対応する必要があります。

## ジョブの復旧

保存完了したローカル認識の未完了ジョブは、再起動時に同じジョブIDで先頭から再実行します。処理区間の途中やモデルのメモリ状態から再開する方式ではありません。

- 音声の保存完了記録・容量・SHA256、管理対象モデルと用途を確認します。欠落・不整合は`interrupted`と`metadata.recoveryBlockedReason`へ記録し、推測で再実行しません。
- `complete`・`cancelled`・`error`・過去の`interrupted`を自動再実行しません。外部有料APIとアップロード未完了も対象外です。
- `queued`・`running`、または保存完了直後でキュー投入前だった`uploading`が対象です。正常停止以外で残った要求も対象になります。自動復旧は同じジョブにつき3回までです。
- 旧ジョブと計測はSQLiteの`restart_attempts`、旧字幕と仮GPU結果は`restart_segments`へ退避します。表示字幕の削除・進捗/時間の初期化・世代更新・再キュー化を同じトランザクションで確定します。媒体を削除しません。
- 起動準備中は復旧ジョブも動かさず、認識環境の準備後に通常スケジューラーへ戻します。RAM/VRAM予算とリアルタイム優先は通常どおりです。

### クライアント契約

`health.capabilities.restartRecovery=true`、`recoveryPolicy.mode=same-id-replay`で検出します。`protocolVersion=3`を維持します。

- jobの`metadata.resultGeneration`は初回0、復旧時に増えます。`metadata.recoveryCount`・`recoveredAt`・`recoveryReason=server_restart`、`status=queued, phase=recovered`で再実行を通知します。
- 字幕ページにもトップレベル`resultGeneration`を返します。世代変更時は表示字幕と`after`カーソルを破棄し、`after=0`から取得してください。jobと字幕ページの間で再起動し得るため、ページの世代を検査して混在を防ぎます。
- 接続切断はジョブ取消ではありません。同じIDへのGETを再接続後に再開してください。POSTの自動再送による別IDの重複ジョブ作成を避けてください。
- HTTP応答そのものや`/v1/audio/transcriptions`の同期接続は復元しません。受付応答前に切断された場合のクライアント再送の同一化、アップロードの途中再送、停止中のリアルタイム音声保持は今回未対応です。

## 完了待ちと更新

新規受付停止（draining）と認識停止は別です。draining中も受付済みの待機・実行・転送を継続し、DBの未完了件数・転送数・ワーカー終了確認がすべて0になるまで待ちます。新規POSTは503と`Retry-After: 5`を返し、GETと既存ジョブの中止を維持します。

サーバーPC限定・既存の操作認証付きで次を利用します。認証トークンをファイルやログへ保存しません。

| 操作 | 本文 |
|---|---|
| `POST /api/admin/drain` | `{"action":"shutdown","confirm":"drain-server"}` |
| `POST /api/admin/drain` | actionを`restart`にすると完了後再起動、`hold`にすると完了後も受付停止を維持 |
| `POST /api/admin/drain/cancel` | `{"id":"開始時に返されたid"}` |

`health.lifecycle`と管理APIの`lifecycle`へ`active`・`id`・`purpose`・`state`・`jobsRemaining`・`uploadsRemaining`を返します。待機中は取消可能ですが、終了/更新の確定（`stopping`）後は取消できません。管理画面の「停止」はこの流れを使用します。

自己更新は取得・検証後に完了待ちへ入り、完了後だけバックアップ/更新ヘルパーへ渡します。資源待ち等で処理が終わらなければ待機し続け、強制終了はしません。待機を取消す場合は新規受付を再開します。

## 手動インストーラー

候補のインストーラーは更新開始前に同梱Rustヘルパーを起動し、導入先の識別情報とサーバーの実PID・実行ファイル・作成時刻を確認します。新しいサーバーは完了待ちAPI、旧版は処理中拒否のある正常終了APIを使用します。旧版は新規受付の停止に未対応なので、連続して要求が来る場合はクライアント側の送信を止めてください。対象不一致・応答不能・取消・正常停止失敗ではファイル更新へ進みません。

Bearer構成では認証キーを推測・複製せず、サーバーPC上で管理者が手動停止するよう案内して終了します。自己更新は既存の認証情報を持つサーバーから実行できます。証明書検証の無効化やサービスの強制停止を行いません。

インストーラーヘルパーの構文/署名確認とコード検証は実施しましたが、新版setupのOS実適用・GUI/ショートカットの実操作・Bearer/HTTPS別PCでの受入は未実施です。
